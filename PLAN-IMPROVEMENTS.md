# Galaxy Admin — анализ и план улучшений

Дата: 14.10.2026. Ветка: `Z2` (последняя, HEAD `abf1faf`).
Проанализированы: все исходники на текущей ветке, история коммитов, обе JSON-выгрузки
в корне репозитория. Ключевые падения воспроизведены в браузере, не только найдены чтением кода.

### Стек и архитектура
Чистый HTML/CSS/JS без сборки и зависимостей, данные — в localStorage
(`galaxy_admin_db_v1`), открывается как файл. Слои: `js/store.js` (данные),
`js/ui.js` (DOM-хелперы, модалки), `js/pages/*` (страницы), `js/app.js` (hash-роутер).

### Что уже хорошо
- Чёткое разделение слоёв, единые хелперы таблиц/модалок — код легко читать.
- `sanitize()` + `pruneRefs()`: база всегда согласованная, старые выгрузки читаются.
- Проверки использования при удалении (свойство/слот/категория не удалятся «в тишь»).
- Редактор слотов корабля: drag&drop, повторы, бейдж занятости, кламп количества по массе.
- Экспорт/импорт как round-trip через санитизацию.

## 2. Критичное: ветка Z2 сломана посередине миграции

Коммит `abf1faf` («#») перевёл на модель «Товары» только часть `store.js`
(`sanitize`, `pruneRefs`, `slotUsage`, `categoryUsage`). Не тронутыми остались
`counts()`, доступеры `resources`/`equipments`, `usedMass()`, `createObject()`,
`demoData()` и вообще все страницы. `PLAN-Z2.md` помечен «не начат», фактически
миграция начата и остановлена на половине слоя данных.

Итог — рабочая ветка не запускается:

| # | Что ломается | Место | Причина |
|---|---|---|---|
| 1 | «Главная» не открывается — пустая страница (**проверено в браузере**) | `store.js: counts()` | читает `d.resources`/`d.equipments`, которых после `blank()` не существует → TypeError |
| 2 | Страницы «Ресурсы»/«Оборудование» падают при открытии | `store.js: Store.resources()/equipments()` | `all('resources')` → `undefined`, дальше `.filter` падает |
| 3 | Удаление любого слота падает | `catalogs.js: deleteSlot()` | ждёт `u.resources`/`u.equipments`, а `slotUsage()` теперь возвращает `{ships, goods}` |
| 4 | Список кораблей падает, если у корабля есть содержимое слотов | `objects.js` колонка «Слоты» | `byId('resources'\|'equipments')` по несуществующей коллекции |
| 5 | Редактор корабля с содержимым падает | `objects.js: compatibleItems/usedNow`, `store.js: usedMass()` | те же несуществующие коллекции |
| 6 | «Загрузить демо-данные» падает | `store.js: demoData()` | `d['resources'].push` — ключа больше нет; плюс демо-категории всё ещё `resource`/`equipment` |
| 7 | Рассинхрон целевой модели | `store.js: createObject('ships')`, `objects.js: collect()` | по-прежнему пишут `kind`, хотя `sanitize` его уже отбрасывает |

Вывод: работать на Z2 дальше нельзя, пока миграция не завершена. Это этап 0.

## 3. План улучшений

### Этап 0 — завершить миграцию «Товары» (P0, блокер), ~1–2 часа
Полностью по `PLAN-Z2.md` (§3–§5). Конкретно осталось:

1. `store.js`: `counts()` → `goods`; доступер `Store.goods()` вместо
   `resources()`/`equipments()`; `usedMass()` и `createObject('ships')` без `kind`;
   `demoData()` на goods (категории `type:'goods'`, содержимое без `kind`).
2. `app.js`: маршруты `#/goods` и `#/categories/goods`; убрать resource/equipment
   (неизвестные хэши и так падают на fallback `#/home`).
3. `objects.js`: одна страница «Товары» и одна модалка без селектора типа;
   `buildSlotsSection`/`addContentRow` без `kind`; совместимость «товар → слот»
   по `slotId` как раньше.
4. `catalogs.js`: `CATEGORY_META` = ship/goods; `deleteSlot()` под новый
   `slotUsage()` (`{ships, goods}`).
5. `home.js`: карточка «Товары», обновлённые тексты «с чего начать».
6. `styles.css`: убрать ставшие ненужными стили селектора типа (опционально).
7. Пометить в `PLAN-Z2.md`, что план выполнен.

**Проверка** (по PLAN-Z2 §5 + фикстуры уже в репозитории):
- импорт `galaxy-admin-data.json` и `galaxy-admin-data (1).json` (оба — master-формат:
  `resources`+`equipments`, слоты без capacity/contents) → товары объединены, ссылки целы;
- round-trip: экспорт → импорт → структура не меняется;
- демо-данные, удаление слота/категории/товара, перегрузка слота, смена слота с очисткой содержимого.
- Коммит с осмысленным сообщением: `feat: merge resources and equipment into goods`.

### Этап 3 — развитие (P3, по потребности)
1. Просмотр «Совместимость»: у корабля — какие товары встанут в каждый его слот;

2. Сохранение базы в JSON-файл через File System Access API (Chromium):
   автосохранение в файл, localStorage — фолбэк. Снимает главный риск проекта —
   потерю данных из localStorage.
3. Автобэкап: последние 5–10 состояний базы в localStorage + восстановление на «Главной».
4. Мини-тесты без Node: страница `tests.html` с прогонами Store (миграция фикстур → goods,
   кламп по вместимости, round-trip) и результатами «зелёный/красный» прямо в браузере.

   возможно, осознанно; тогда оставить как есть).

### Ограничения, которые сохраняем
Без Node.js, без серверных БД и сборки; данные — только локально
(localStorage + JSON-файлы). Все пункты плана соблюдают эти рамки.
