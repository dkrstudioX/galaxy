# Карта Солнечной системы в реальном масштабе

> **Статус: реализовано.** 24.10.2026. Ветка `feat/space-real-scale`.
>
> Цель — перевести карту `space/` на единый реальный масштаб: размеры всех
> небесных тел и расстояния между ними соответствуют реальным, а положения
> планет считаются по симметричной кеплеровской модели.
>
> Итог: единый масштаб `1 а.е. = 1000 wu`, 8 планет и 456 лун, LOD-маркеры и
> группы, пресеты камеры, HUD «км/px» и «px/а.е.», базы на реальных радиусах.
> Проверено в браузере: стартовый вид, виды планет/лун/поясов, карточки,
> дерево с фильтром, создание/перенос/удаление баз; ошибок в консоли нет.

## Цель

Сейчас карта сжата: у планет `r = 4…22` условных единиц, орбиты — `70…780`,
Солнце — `22`, луны сжаты логарифмически, а `auToDist` — кусочно-линейная
шкала. В результате Земля больше Луны в 2,7 раза, а Нептун всего в 11 раз
дальше Земли. Нужно, чтобы карта показывала реальные пропорции:

- единый линейный масштаб для расстояний и для радиусов тел;
- Солнце, 8 планет, **все известные луны**, именованные астероиды, ОЗА,
  троянцы и кометы — с реальными радиусами и орбитальными элементами;
- симметричные эклиптические долготы планет (0°, 45°, … 315°) на эпоху
  `2026-10-23`, как в `space/data/planet-positions.json`;
- карта остаётся читаемой: на общем плане тела меньше пикселя, поэтому
  вводится LOD — настоящий диск при достаточном зуме, иначе маркер
  видимости.

## Принятые решения

1. **Единый масштаб.** `1 а.е. = 1000` мировых единиц (wu).
   `1 км = 1000 / 149 597 870.7 = 6.684587e-6` wu.
   И расстояния, и радиусы считаются по этой константе. Никаких отдельных
   «визуальных» радиусов и сжатых орбит.
2. **Симметрия планет.** В `data.js` переносятся `m0`/`l0`, пересчитанные на
   J2000 так, чтобы на эпоху `2026-10-23T00:00Z` истинные эклиптические
   долготы были 0°, 45°, 90°, … 315°. Значения уже посчитаны (таблица ниже),
   движение — тем же уравнением Кеплера с реальными `e`, `peri`, `inc`, `node`.
3. **LOD вместо искажения масштаба.** Тело рисуется настоящей сферой, когда
   его экранный радиус ≥ 1.25 px. Иначе — маркер видимости: полое кольцо
   фиксированного экранного размера. Если маркер ближе 28 px к более
   массивному телу, он не рисуется отдельно, а входит в группу этого тела
   (у Солнца — «Внутренние планеты · 4», у планеты — её луны). Маркер —
   элемент интерфейса, а не «увеличенное тело»; в HUD и легенде это
   подписано. Подписи есть у всех тел; `placeLabel` разводит их по вертикали.
4. **Пыль поясов — не тела.** Частицы главного пояса, Койпера и Оорта остаются
   визуализацией плотности (фиксированный экранный размер точки). Реальные
   радиусы есть только у именованных тел. Облако Оорта на карте остаётся
   плоским кольцом — это проекция сферической оболочки, а не её форма.
5. **Камера.** Линейный мировой масштаб, зум `1e-6 … 10000` (px/wu),
   стартовый вид — по орбите Марса (внутренняя система). Добавляются
   пресеты масштаба, шкала «км/px» и «px/а.е.».
6. **Базы.** Радиус орбиты — 3 радиуса хозяина, период игровой (один виток
   в сутки на стартовом радиусе). Базы разрешены только на телах с радиусом
   ≥ 50 км; старые записи в `localStorage` мигрируют один раз.
7. **UI — оба формата.** HUD показывает «1 px = N км» и «N px/а.е.»;
   карточки — радиус/диаметр в км, орбиту и расстояние в а.е., угловой
   размер в угловых секундах (в модели).

## Единицы и данные

Новый модуль `space/js/units.js` (первым в `build.py` после `config`):

```js
export const AU_KM = 149597870.7;
export const AU_WU = 1000;                       // 1 а.е. = 1000 wu
export const KM_WU = AU_WU / AU_KM;              // 6.684587e-6 wu/км
export const au = v => v * AU_WU;
export const km = v => v * KM_WU;
export const wuToKm = v => v / KM_WU;
export const wuToAu = v => v / AU_WU;
```

`config.js`:

- `SUN_R` → `km(696340)` = 4.654745 wu (импорт из `units.js`);
- `MIN_ZOOM = 1e-6`, `MAX_ZOOM = 10000`;
- `TRUE_MIN_PX = 1.25` — порог «настоящего диска»;
- `MARKER_PX = { sun: 3.0, planet: 2.6, moon: 2.0, small: 1.6 }`;
- `BASE_ORBIT_K = 3`, `BASE_CLEAR_K = 0.4`, `BASE_SAME_GAP_K = 0.25` — доли
  радиуса хозяина для баз;
- `BASE_MIN_HOST_KM = 50` — минимальный радиус тела, на котором можно
  создать базу.

### Все луны: каталог и генератор

Ручной `moonsByPlanet` (24 луны) заменяется каталогом. Источник:

- орбитальные элементы — JPL SSD «Planetary Satellite Mean Elements»
  (`https://ssd.jpl.nasa.gov/sats/elem/`): `a`, `e`, `ω`, `M`, `i`, `node`,
  `P`, система отсчёта;
- средние радиусы — JPL «Planetary Satellite Physical Parameters»
  (`https://ssd.jpl.nasa.gov/sats/phys_par/`) и Wikipedia «List of natural
  satellites» для именованных лун, у которых в JPL радиуса нет;
- Плутон и его луны не входят: Плутона нет на карте.

Объём: **456 лун** у шести планет (Земля 1, Марс 2, Юпитер 115, Сатурн 292,
Уран 30, Нептун 16). Средний радиус есть у всех 456: 41 значение из JPL,
остальные — из Wikipedia «List of natural satellites» (включая 29 совпадений
по нечёткому имени, например `S2010_J_1` ↔ провизорное обозначение).
Оценок и флагов `radEstimated` не требуется.

Прежние счётчики 454/290 были ошибкой разбора: скрипт отбрасывал обратные
луны с отрицательным периодом в таблице JPL. Теперь период берётся по
модулю (`|P|`), а направление движения задаётся наклонением `inc > 90°`,
поэтому все 292 спутника Сатурна на месте.

Генератор `space/data/build-moons.py` (лежит в репозитории) скачивает обе
таблицы, соединяет по коду спутника и пишет `space/js/moons_data.js`:

```js
// СГЕНЕРИРОВАНО build-moons.py — не редактировать вручную.
export const moonCatalog = [
  { planet: 'Earth', n: 'Moon', ru: 'Луна', a: 384400, e: 0.0554,
    peri: 83.23, m0: 135.27, inc: 5.16, node: 125.08, period: 27.322,
    rad: 1737.4, frame: 'ecliptic' },
  // … 456 записей
];
```

Поля: `a` и `rad` — км, `peri = ω + node` (долгота перигелия в плоскости
орбиты), `m0 = M` на J2000, `inc`/`node` — как в таблице JPL (Laplace,
эклиптика или экватор — поле `frame`), `period` — сутки. `ru` заполняется
для крупных лун из текущего списка, остальные показываются латиницей.

`data.js` из каталога собирает:

- `moonsByPlanet` — та же структура `{ n, period, a, r, c, inc, node }`,
  плюс `e`, `peri`, `m0`, `rad`, `ru`; `r = km(rad)`;
- `moonTree` — группы по планете, крупные луны первыми, полный список — по
  раскрытию; счётчики из каталога;
- `moonTotals` — реальные числа (1, 2, 115, 292, 30, 16);
- `moonOrbitRadius(p, i)` → `km(m.a)`, без логарифмического сжатия.

Луна Земли больше не отдельный блок в `render.js`: она входит в общий
каталог и рисуется тем же путём. `moonDist` остаётся экспортом
(`km(384400)` = 2.569555) для баз и тестов.

Движение лун — не круговая `phase`, а те же кеплеровские элементы:
`keplerPos3(m.a_wu, m.e, m.peri, m.m0, m.period, simDays)` относительно
планеты, с `inc`/`node`. Орбитальные полилинии лун кэшируются в локальных
координатах (смещение от планеты) и только сдвигаются каждый кадр — иначе
456 лун × 128 точек на кадр слишком дорого.

### Малые тела

`beltNotables`, `neas`, `comets` уже хранят диаметр `dia` — радиус берётся
как `km(dia / 2)`. Троянцам добавляются реальные диаметры (Ахиллес 135,
Агамемнон 167, Гектор 225, Патрокл 140 км). Ядра комет: Галлея 11, Энке 4.8,
Свифта—Таттла 26, Хейла—Боппа 60 км — уже есть.

`math.js`: `AU_ANCHORS` и кусочный `auToDist` удаляются, остаётся
`auToDist(v) = au(v)`; `keplerPos`/`keplerPos3` для планет продолжают получать
`mapDist = v => v`, но `a` теперь в wu. Для малых тел `mapDist` по умолчанию —
линейный `auToDist`.

## Камера и зум

- Стартовый зум: вписать орбиту Марса с запасом 5 % —
  `fitZoom(au(1.523679))`, примерно `0.28` при высоте 900 px.
- `MIN_ZOOM = 1e-6` — внешний край Оорта (100 000 а.е. = 1e8 wu) занимает
  около 100 px; `MAX_ZOOM = 10000` — Земля 426 px, Луна 116 px, Церера
  31 px, Фобос 0.74 px (маркер).
- `zoomAt` и `updateFlyTo` уже работают геометрически; добавляется
  адаптивный шаг колеса: при `zoom < 0.01` множитель 1.25 вместо 1.1, чтобы
  не крутить колесо сотни раз.
- Пресеты (кнопки в `#controls`, стиль `.btn`):
  «Внутренние» (Марс, `0.28` — стартовый), «Планеты» (Нептун, `0.015`),
  «Пояс» (`0.12`), «Койпер» (`0.008`), «Оорт» (`4.5e-6`), «Солнце» (`70`).
- `VIEW_TARGETS` в `ui.js`:
  - `sun` — вписать диск Солнца: `fitZoom(SUN_R * 1.3) ≈ 70`;
  - `planet` — вписать внешнюю **крупную** луну (радиус ≥ 100 км) или
    `20R`, если лун нет; при этом диск планеты не меньше 8 px:
    Земля ≈ 159, Юпитер ≈ 17, Сатурн ≈ 21, Меркурий ≈ 1380;
  - `moon` — `clamp(40 / m.r, 20, MAX_ZOOM)` (Луна ≈ 3445, Фобос — предел);
  - `asteroid`, `nea`, `trojan`, `comet` — `MAX_ZOOM` (маркер + карточка;
    Церера, Веста и Паллада при этом видны диском);
  - `belt` — `fitZoom(au(3.5)) ≈ 0.12`, `kuiper` — `fitZoom(au(50)) ≈ 0.008`,
    `oort` — `fitZoom(au(100000))` с ограничением `MIN_ZOOM`.
- HUD: вместо `ZOOM: 1.0x` — две строки: «1 px = N км» (при больших
  значениях — «N а.е.») и «N px/а.е.», плюс линейка масштаба внизу слева.
  Форматтеры в `math.js`.

## LOD: что видно при каком зуме

Правило общее: экранный радиус `rPx = r * zoom`.

1. `rPx ≥ TRUE_MIN_PX` — настоящая сфера с подсветкой и тенью (как сейчас).
2. `rPx < TRUE_MIN_PX` — маркер видимости: полое кольцо `MARKER_PX.planet`
   у планет и Солнца, полое кольцо меньшего размера у лун и малых тел.
   Позиция — строго реальная; размер маркера от масштаба не зависит.
3. Группировка: если маркер ближе 28 px к маркеру более массивного тела,
   отдельный маркер не рисуется — тело входит в группу. У Солнца это
   «Внутренние планеты · 4», у планеты — её луны. Групповое кольцо имеет
   радиус по самому дальнему участнику и подпись «Имя · N». При зуме группа
   автоматически распадается на отдельные тела по тому же порогу. На виде
   Койпера/Оорта вся планетная система — одна группа «Солнечная система».
   Клик по групповому кольцу открывает компактный список тел группы в
   карточке; клик по строке — полёт к телу (`flyToCamera`).
4. Кольцевые слои (пояс, Койпер, Оорт) рисуются, когда радиус кольца на
   экране ≥ 40 px; иначе — одна тонкая окружность-подсказка без частиц.
5. Луны и малые тела попадают в кадр, только если их орбита на экране ≥ 2 px
   и она пересекает видимую область. Для 456 лун это обязательное условие:
   иначе внешние иррегулярные спутники Сатурна (до 30 млн км) будут
   считаться вхолостую. Это же правило убирает «облако» точек на общем плане.
6. Подписи есть у всех видимых тел и групп; `placeLabel` разводит их по
   вертикали без наложений. Внутри группы подписи отдельных тел не рисуются —
   их имена в списке группы.
7. Солнце: настоящая сфера при `zoom ≥ 0.27`; иначе маркер + экранное гало
   диаметром не меньше 24 px, чтобы звезда была видна на общем плане.
8. Мировые звёзды `drawStars` из `render.js`/`scene.js` удаляются: на широком
   зуме они всё равно схлопываются в точку, а экранный слой `sky.js` уже
   рисует звёзды с параллаксом.

`hover.js`: минимальные радиусы попадания остаются экранными
(`MIN_HIT_PLANET_PX`, `MIN_HIT_MOON_PX`), но у мелких тел hit-радиус не
меньше `MARKER_PX`; при совпадении маркеров выбирается ближайший к курсору.
Групповое кольцо — отдельная hit-цель (`kind: 'group'`): hover показывает
«Внутренние планеты · 4», клик открывает список тел группы. Орбита
наведённого тела рисуется как сейчас.

## Малые тела

- `BELT_MIN/MAX` → `auToDist(2.2)` / `auToDist(3.5)` = 2200 / 3500 wu.
  Щели Кирквуда уже заданы в а.е. и пересчитываются автоматически.
- Частицы пояса: `s` трактуется как экранный размер (0.6–1.8 px) и делится на
  `zoom` при отрисовке; иначе при общем плане они исчезают.
- Койпер: `auToDist(30 + rng*20)` = 30 000–50 000 wu.
- Оорт: вместо `1300 + rng*500` — `auToDist(2000 + rng^2 * 98000)`, то есть
  2 000–100 000 а.е.; `REGION_BOUNDS.oort` = { 2e6, 1e8 } wu.
- Троянцы: центр облака считается от фактической долготы Юпитера (из его
  позиции), а не от `orbitAngle(JUPITER.l0)`, иначе облако сдвинется на
  уравнение центра.
- Кометы: `a` уже в а.е., `auToDist` линейный; хвост остаётся декоративным
  (экранная длина), ядро — настоящая сфера или маркер.
- Карточки `ui.js`: «Радиус» и «Диаметр» в км, «Большая полуось» в а.е.,
  «Расстояние до Солнца» в а.е. (для текущего кадра — `rAu`), «Угловой
  диаметр» в угловых секундах. У области Оорта — «2 000–100 000 а.е.».

## Базы

- `baseRadiusRange(host)` пересчитывается в реальных величинах:
  `min = hostR * (1 + BASE_CLEAR_K)`, `max` — ближайшая **крупная** луна
  (радиус ≥ 50 км), планета или Солнце минус их радиус и запас;
  `BASE_MAX_R` заменяется на `hostR * 8` (или ближайшую границу).
- Уточнение при реализации: у базы **на планете** орбиты крупных лун не
  обрывают коридор, а становятся запретными полосами внутри него
  (`moonBands` + `fitRadius`, запас `BASE_MOON_CLEAR_K = 0.1` радиуса
  хозяина). Иначе 3R Юпитера (1.40 wu) не влезает внутрь орбиты Амальтеи
  (1.21 wu), и стартовый радиус пришлось бы прижимать к планете. База стоит
  на одном радиусе, поэтому между орбитами лун она безопасна, а на радиус
  луны не встаёт. У базы на луне ограничение `max` осталось прежним.
- Стартовая орбита базы: `BASE_ORBIT_K * hostR` (3 радиуса хозяина).
  Для Земли 0.128 wu, для Луны 0.035 wu, для Юпитера 1.40 wu.
  Если 3R занят другой базой хозяина (например, legacy `LUNA-ORBIT` у Луны),
  `fitRadius` отодвигает новую базу на зазор `BASE_SAME_GAP_K * hostR`.
- `BASE_CLEAR`, `BASE_SAME_GAP` — доли `hostR` (0.4 и 0.25), а не абсолютные
  4 и 3 wu.
- `fitRadius` округляет не до 0.1, а до 4 значащих цифр
  (`Number(want.toPrecision(4))`) — иначе радиусы лун обнуляются.
- Период базы остаётся игровым: один виток в сутки на стартовом радиусе,
  дальше `r^1.5`. Это не астрономическая величина и в реальный масштаб не
  входит.
- Базы на лунах с радиусом < 50 км не создаются: кнопка «Создать базу»
  скрыта, в карточке — «тело слишком мало для базы». У таких лун орбита
  базы была бы меньше пикселя даже на максимальном зуме.
- Миграция `localStorage`: у записи появляется `scale: 2`. Если поле
  отсутствует, `orbitRadius` сбрасывается на `BASE_ORBIT_K * hostR`,
  период пересчитывается; `id`, имя, статус, `fleet` и фаза сохраняются.
  `LUNA-ORBIT` создаётся сразу с новым радиусом.
- Отрисовка маркера базы (`diamond`, `LIFT.base`) уже экранная — не меняется.

## JSON

`space/data/planet-positions.json` приводится к тому же масштабу:

- `orbit.semiMajorAxisMap` = `aAu * 1000`;
- `positionMap` = `positionAu * 1000` (x, y, z), `distanceMap` — так же;
- добавляются `radiusKm` и `radiusMap` для Солнца и планет;
- `model.units.positionMap` = «world units, 1 а.е. = 1000»;
- `schema` → `galaxy.planet-positions/2`.

JSON остаётся справочным файлом: карта считает положения из `data.js`, а не
читает JSON (как и сейчас). Каталог лун — отдельный `space/js/moons_data.js`,
сгенерированный `build-moons.py`.

## Риски и как снимаем

- **Пустая карта на общем плане.** Снимается маркерами и пресетами; маркеры
  явно подписаны как видимость, а не как размер.
- **Десять порядков зума.** Стартовый вид и пресеты; геометрический полёт
  камеры уже есть; адаптивный шаг колеса.
- **456 лун и производительность.** Кэш локальных орбит, culling по
  экранному радиусу и видимой области, группировка; дерево — по раскрытию.
- **Точность canvas при `zoom 1e-6`.** Мировые координаты ≤ 1e8, `scale`
  двойной точности; линии и подписи компенсируются делением на `zoom`.
- **Радиусы мелких лун.** У всех 456 есть средний радиус, но у мелких он
  измерен грубо (±десятки процентов). Для карты это несущественно: такие
  тела всё равно маркеры, а в карточке значение показывается как есть.
- **Старые базы в `localStorage`.** Одноразовая миграция по `scale: 2`,
  сохраняются имена и статусы.
- **Производительность Оорта.** 350 точек пыли, culling по камере уже есть;
  при общем плане частицы пояса не рисуются.
